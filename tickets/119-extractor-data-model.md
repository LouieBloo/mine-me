# 119 - Extractor data model and loader

**Priority:** P1 - **Status:** Open - **Depends on:** none

## Decisions (2026-10-22, from the owner)
- **Data-driven rates on an `Extractor` definition** (belt speed, unload rate, build rate, shaft width, health numbers), so later upgrades just swap or scale the definition. No constants in logic.
- Player upgrades to build faster come later; the model must make that a data change.

## Proposed design
- `Extractor` table: `key`, `name`, `textureUrl` (`/assets/...`), `width/height` footprint (small blocks), `landingSound`/`loopSound` slots (sound library, per-slot `volume`), `landingParticleEffectId`, belt fields: `shaftWidth` (default 3 blocks), `buildSecondsPerSegment`, `beltSpeed` (cells/s), `unloadItemsPerSecond`, `beltSegmentHealth`, `isDefault`.
- Shared type `ExtractorDefinition`; loader in `definitionLoaders`, reloaded after admin save; JSON dev mirror only.
- An `ExtractorUpgrade` concept is reserved (a multiplier set on a character/profession effect) but not built.
- All distances/speeds follow the block-scale rule: original value x `BLOCK_SCALE`; pixel sizes stay pixels.

## Tests
Loader, validation (positive rates, width >= 1), default fallback.
